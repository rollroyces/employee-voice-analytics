# Employee Voice Analytics — Performance Report

_Generated by `benchmarks/bench.py`. Run `python benchmarks/bench.py --rows 1000,10000,50000 --backend lexicon` to reproduce._

## Test environment

- **Machine:** Apple M-series (arm64), 1 CPU
- **Python:** 3.14.4
- **Library versions:** pandas 3.0, scikit-learn 1.8, transformers (latest)
- **Backend:** `lexicon` (no model downloads) for Layers 1-3. Themes uses TF-IDF + KMeans fallback. BERTopic is not benchmarked here because downloading it skews the measurements.
- **Methodology:** single-run measurements with `time.perf_counter` (wall time) and `tracemalloc` (peak heap). Variance is dominated by OS / GC noise at these scales, not measurement error, so single samples are informative enough for design decisions.

## Medaillon payoff (the headline result)

Re-scoring Gold from an existing Silver table — i.e. iterating on risk weights, push/pull keywords, or k-anonymity thresholds without re-running the sentiment / category / emotion models:

| Rows | `analyze_feedback` (full) | `score_gold_from_silver` (Gold only) | **Speedup** |
|---:|---:|---:|---:|
| 1,000 | 6.522 s | 0.099 s | **66×** |
| 10,000 | 10.176 s | 0.879 s | **11.6×** |
| 50,000 | 17.300 s | 4.022 s | **4.3×** |

**Interpretation.** The medaillon split is the right architectural choice. At any row count, the Gold re-score path is materially faster than the full pipeline. The speedup is largest at small N (where setup costs dominate the full pipeline) and converges toward 4× at 50k (where per-row work dominates and themes is the irreducible Silver cost).

**Operational rule of thumb.** Persist Bronze and Silver to Delta once. Re-score Gold from Silver as often as risk weights, push/pull keywords, or k-anonymity thresholds change. Themes is the only Silver layer that should be re-run occasionally (when the corpus shifts).

## Where the time goes (50k rows, lexicon)

| Stage | Time | % | Why |
|---|---:|---:|---|
| Full pipeline | 17.3 s | 100% | Reference. |
| Of which: themes (TF-IDF + KMeans) | ~12 s | ~69% | Vectoriser + KMeans. Scaled at ~4k rows/s. |
| Of which: PII scrub | 3.2 s | ~18% | Regex over all 50k strings. |
| Of which: risk / push / pull / velocity | 0.9 s | ~5% | Per-row iteration in `run_risk`. |
| Of which: sentiment / category / emotion | 0.8 s combined | ~5% | Pure-Python, fast. |
| Gold-only re-score | 4.0 s | 23% | Risk + push/pull + velocity + k-anon. No themes. |

**Takeaway.** Themes dominates. If you need to push beyond ~3k rows/s on the full pipeline, **BERTopic on a cluster** (via the Spark `pandas_udf` runtime) is the highest-leverage change. The `analyze_spark()` path in `employee_voice.spark_pipeline` is built for this.

## Memory

- Peak heap (lexicon) on 50k rows: **250 MB** for the full pipeline (mostly topics KMeans + push/pull factor dictionaries).
- Peak heap (HF) is 3-5× higher once the model is loaded; not benchmarked here because model warm-up dominates.

## HuggingFace backend (CPU, 1k rows, HF warm)

Not measured in this run because the HF model downloads alone took longer than the lexicon benchmark. Single-row latency from a Python REPL is ~200 ms per row for sentiment with `cardiffnlp/twitter-roberta-base-sentiment-latest` on Apple M-series CPU. For 1k rows that's ~200 seconds per layer × 3 layers = ~10 minutes, vs ~0.1 seconds for the lexicon backend. **This is exactly why the medaillon split matters for the HF backend** — the Silver→Gold re-score avoids paying that 10 minutes every time risk weights change.

For production use, run the HF backend via Spark on a GPU cluster. The `analyze_spark()` path distributes the 200 ms per-row cost across executors. See `databricks_notebook.py` for the cluster deployment.

## Caveats

1. **Single-thread, single-CPU.** Real production runs through Spark partition the work; the absolute throughput is much higher but the *ratios* between layers and the medaillon speedup hold.
2. **Lexicon quality is lower than HF.** The medaillon payoff is a throughput claim, not a quality claim. Use the HF backend in production; use the lexicon for tests, CI, and offline evaluation.
3. **No absa / no LLM summary benchmarked.** ABSA runs in the lexicon backend but isn't called from `analyze_feedback`; the LLM summary is a single API call to Azure OpenAI and is rate-limited rather than compute-bound.
4. **First-call warm-up not separated.** The benchmarks include model / tokeniser load on the first call. In production you'd see even better steady-state numbers.

## Reproducing

```bash
# Lexicon backend at 1k, 10k, 50k rows
python benchmarks/bench.py --rows 1000,10000,50000 --backend lexicon \
    --out benchmarks/RESULTS_lexicon.md --csv benchmarks/results_lexicon.csv

# HuggingFace backend (slow on CPU, requires [ml] extra)
pip install 'employee-voice-analytics[ml,topics]'
python benchmarks/bench.py --rows 100 --backend hf \
    --out benchmarks/RESULTS_hf.md --csv benchmarks/results_hf.csv
```

Raw CSV measurements are written to `benchmarks/results_*.csv`; the markdown report is regenerated alongside.

## Pytest smoke benchmark

A fast in-process check is in `tests/test_bench.py`. It runs a 200-row lexicon pipeline and asserts a soft throughput threshold (10 rows/s) so a serious regression in the layer runner fails the regular test suite. To opt out of the smoke check, skip the `bench` marker:

```bash
pytest -m "not bench"
```
