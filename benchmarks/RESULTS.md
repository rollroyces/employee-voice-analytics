# Employee Voice Analytics — Performance Report

_Generated by `benchmarks/bench.py`. Run `python benchmarks/bench.py --rows 1000,10000,50000 --backend lexicon` to reproduce the lexicon numbers, and `python benchmarks/bench_hf.py --rows 100` for the HF numbers._

## Headline: Medaillon speedup (lexicon, single CPU)

| Rows | `analyze_feedback` (full) | `score_gold_from_silver` (Gold only) | **Speedup** |
|---:|---:|---:|---:|
| 1,000 | 6.52 s | 0.10 s | **66×** |
| 10,000 | 10.18 s | 0.88 s | **11.6×** |
| 50,000 | 17.30 s | 4.02 s | **4.3×** |

Re-scoring Gold from a persisted Silver table (after risk-weight or k-anonymity changes) is the right operational pattern. The benchmark harness even asserts this as an invariant: two consecutive `score_gold()` calls on the same Silver must produce identical `RiskScore` columns.

## Headline: HF backend (Apple M-series MPS, 100 rows, steady state)

| Layer | rows/sec | Time for 1M rows (single CPU) |
|---|---:|---|
| `sentiment` (RoBERTa) | 22.2 | ~12.5 hours |
| `category` (BART-MNLI zero-shot) | **1.5** | **~7.7 days** |
| `emotion` (GoEmotions) | 24.2 | ~11.5 hours |

**Category is the bottleneck** on a single machine. **This is why the medaillon split matters for the HF backend**: persisting Silver and re-scoring Gold from it is the only way the HF backend is operationally viable. A k-anonymity threshold change takes milliseconds; a full Silver re-run takes days.

Numbers are produced by `benchmarks/bench_hf.py` (one subprocess per layer, warmup + measure pattern, child prints a parseable `MEASURE` line the parent parses). See [`RESULTS_hf.md`](./RESULTS_hf.md) for the full HF report.

For production, run HF on a Spark cluster via `analyze_spark()`. The `pandas_udf(SCALAR_ITER)` runtime parallelises per-row inference across executors.

### Category model choice (HF backend)

The category layer is the bottleneck. Distilling BART-MNLI to a smaller NLI model gives a 2-5× speedup on a single machine. See [`RESULTS_category_models.md`](./RESULTS_category_models.md).

| model | params | rows/sec | vs BART |
|---|---:|---:|---:|
| `facebook/bart-large-mnli` (default) | 400M | 1.6 | 1.0× |
| `MoritzLaurer/DeBERTa-v3-base-mnli-fever-anli` | 140M | 3.7 | 2.3× |
| `cross-encoder/nli-deberta-v3-small` | 140M | 4.4 | 2.8× |
| `typeform/distilbert-base-uncased-mnli` | 70M | 9.4 | **5.9×** |

`typeform/distilbert-base-uncased-mnli` is the practical sweet spot when single-machine throughput matters more than top-1 accuracy. Set `CATEGORY_MODEL_ID` in `config.py` to switch.

## Where the time goes (50k rows, lexicon)

| Stage | Time | % | Why |
|---|---:|---:|---|
| Full pipeline | 17.3 s | 100% | Reference. |
| Of which: themes (TF-IDF + KMeans) | ~12 s | ~69% | Vectoriser + KMeans. Scaled at ~4k rows/s. |
| Of which: PII scrub | 3.2 s | ~18% | Regex over all 50k strings. |
| Of which: risk / push / pull / velocity | 0.9 s | ~5% | Per-row iteration in `run_risk`. |
| Of which: sentiment / category / emotion | 0.8 s combined | ~5% | Pure-Python, fast. |
| Gold-only re-score | 4.0 s | 23% | Risk + push/pull + velocity + k-anon. No themes. |

**Takeaway.** Themes dominates. If you need to push beyond ~3k rows/s on the full pipeline, **BERTopic on a cluster** (via the Spark `pandas_udf` runtime) is the highest-leverage change. The `analyze_spark()` path in `employee_voice.spark_pipeline` is built for this.

## Memory

- Peak heap (lexicon) on 50k rows: **250 MB** for the full pipeline (mostly topics KMeans + push/pull factor dictionaries).
- Peak heap (HF) is 3-5× higher once the model is loaded; not benchmarked here because model warm-up dominates.

## HuggingFace backend (Apple M-series, MPS GPU, 100 rows, steady state)

See [`benchmarks/RESULTS_hf.md`](./RESULTS_hf.md) for the full report. Headline:

| Layer | rows/sec | Time for 1M rows (single CPU) |
|---|---:|---|
| `sentiment` (RoBERTa) | 22.7 | ~12 hours |
| `category` (BART-MNLI zero-shot) | 1.5 | **~7.7 days** |
| `emotion` (GoEmotions) | 36.1 | ~7.7 hours |

**Category is the bottleneck** on a single machine — BART-MNLI scores each input against all 18 HR categories. This is why the **medaillon split matters for the HF backend**: persisting Silver and re-scoring Gold from it is the only way the HF backend is operationally viable. A k-anonymity threshold change takes milliseconds; a full Silver re-run takes days.

For production, run HF on a Spark cluster via `analyze_spark()`. The `pandas_udf(SCALAR_ITER)` runtime parallelises per-row inference across executors.

## Caveats

1. **Single-thread, single-CPU.** Real production runs through Spark partition the work; the absolute throughput is much higher but the *ratios* between layers and the medaillon speedup hold.
2. **Lexicon quality is lower than HF.** The medaillon payoff is a throughput claim, not a quality claim. Use the HF backend in production; use the lexicon for tests, CI, and offline evaluation.
3. **No absa / no LLM summary benchmarked.** ABSA runs in the lexicon backend but isn't called from `analyze_feedback`; the LLM summary is a single API call to Azure OpenAI and is rate-limited rather than compute-bound.
4. **First-call warm-up not separated.** The benchmarks include model / tokeniser load on the first call. In production you'd see even better steady-state numbers.

## Reproducing

```bash
# Lexicon backend at 1k, 10k, 50k rows
python benchmarks/bench.py --rows 1000,10000,50000 --backend lexicon \
    --out benchmarks/RESULTS_lexicon.md --csv benchmarks/results_lexicon.csv

# HuggingFace backend (slow on CPU, requires [ml] extra)
pip install 'employee-voice-analytics[ml,topics]'
python benchmarks/bench.py --rows 100 --backend hf \
    --out benchmarks/RESULTS_hf.md --csv benchmarks/results_hf.csv
```

Raw CSV measurements are written to `benchmarks/results_*.csv`; the markdown report is regenerated alongside.

## Pytest smoke benchmark

A fast in-process check is in `tests/test_bench.py`. It runs a 200-row lexicon pipeline and asserts a soft throughput threshold (10 rows/s) so a serious regression in the layer runner fails the regular test suite. To opt out of the smoke check, skip the `bench` marker:

```bash
pytest -m "not bench"
```
